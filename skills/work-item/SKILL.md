# Work Items

현재 범위: 티켓 생성. 이후 기능은 이 파일에 섹션으로 추가한다.

## 티켓 생성

티켓 본문은 사람이 읽는 요약이다. 담당자, 리뷰어, 몇 달 뒤 히스토리를 뒤지는 사람이 몇 줄만 보고 상황을 파악해야 한다. 그래서 본문은 짧게 쓰고, AI가 작업하면서 정리한 상세 내용(분석 과정, 코드 변경 목록, 로그 등)은 본문에 섞지 않고 댓글로 뺀다. 본문은 "무엇을 왜 하는가", 댓글은 "어떻게 처리했는가"다.

### 진행 순서

1. 사용자가 준 내용에서 본문 초안을 먼저 만든다. 질문부터 던지고 티켓을 미루지 않는다.
2. 제목과 생성 여부를 **한 번에** 선택지로 묻는다 (아래 참고). 질문 도구(AskUserQuestion)가 있으면 그걸 쓰고, 없으면 같은 내용을 번호 선택지로 적는다.
3. 답에 따라 생성하거나 텍스트만 준다.
4. 생성했고 시작일·종료일이 비어 있으면 날짜 답으로 필드를 업데이트한다 (아래 "시작일·종료일" 참고).
5. 생성했고 AI가 처리한 상세 내용이 있으면 댓글로 남긴다.
6. 세션에서 코드 작업을 하고 PR을 만들었으면 티켓에 PR 링크를 단다 (아래 "PR 링크" 참고).
7. PR 본문을 쓰는 경우 Jira 본문처럼 짧게 쓴다 (아래 "PR 본문" 참고).

### 선택지로 묻기

질문은 한 번에 묶어서, 최대 네 개 (제목·생성 + 날짜 두 개):

**제목** — 초안 제목을 보여주고 고르게 한다.
- `(초안 제목)` 사용
- 직접 입력 — 사용자가 "Other"로 입력. 선택지 설명에 "직접 입력하려면 Other에 적어주세요"를 넣는다.

**생성** — Jira 커넥터가 있을 때만 묻는다.
- Jira에 바로 생성
- 텍스트만 받기 (붙여넣기용)

**시작일 / 종료일** — 사용자가 날짜를 주지 않았으면 같은 질문 묶음에 넣는다 (형식은 아래 "시작일·종료일").

커넥터가 없으면 생성 질문은 생략하고 제목만 묻는다. 사용자가 이미 "만들어줘/등록해줘"라고 했어도 생성 질문은 한 번 거친다. 잘못 올라간 티켓을 지우는 것보다 한 번 확인하는 게 싸다.

### 시작일·종료일

시작일(Start date)이나 종료일(Due date)이 비어 있으면 묻고 채운다. 새 티켓을 만들 때뿐 아니라 기존 티켓을 다루다 두 필드가 빈 걸 발견해도 같다. 이미 값이 있는 필드는 묻지 않는다.

#### 묻는 형식

날짜 하나당 질문 하나. 선택지 라벨에는 상대 표현과 실제 날짜를 같이 적는다 (오늘 날짜 기준으로 계산). 아래 날짜는 오늘이 2026-10-23(금)일 때의 예시다.

**시작일**
- `2026-10-23 (오늘)`
- `2026-10-26 (다음 주 월요일)`
- 비워두기
- 직접 입력 — 설명에 "`YYYY-MM-DD` 형식으로 Other에 적어주세요"를 넣는다.

**종료일**
- `2026-10-23 (이번 주 금요일)`
- `2026-10-30 (다음 주 금요일)`
- 비워두기
- 직접 입력 — 설명에 "`YYYY-MM-DD` 형식으로 Other에 적어주세요"를 넣는다.

질문 도구가 없으면 같은 선택지를 체크박스 목록(`- [ ] 2026-10-23 (오늘)`)으로 적고, 직접 입력은 `YYYY-MM-DD`로 답해달라고 한 줄 붙인다.

#### 입력 검증

- 직접 입력은 하이픈 구분 `YYYY-MM-DD`만 받는다. `10/30`, `2026.10.30`, `20261030`처럼 다른 형식이면 해석한 날짜를 `YYYY-MM-DD`로 보여주고 맞는지 한 번 확인한다.
- 종료일이 시작일보다 앞이면 업데이트하지 않고 다시 묻는다.
- "비워두기"를 고르면 그 필드는 건드리지 않는다.

#### 업데이트

- 종료일은 시스템 필드 `duedate`. 시작일은 사이트마다 커스텀 필드(`customfield_xxxxx`, 이름 "Start date")라 ID를 먼저 확인한다. 티켓을 `view: full`로 읽거나 editmeta로 필드 이름 → ID를 찾는다. 추측한 ID로 쓰지 않는다.
- 값은 `"2026-10-30"` 문자열 그대로 넣는다. 시간·타임존을 붙이지 않는다.
- 날짜를 미리 받았으면 생성 요청에 같이 넣는다. 화면에 필드가 없어 거부되면 생성 후 edit로 따로 넣는다.
- 업데이트 후 티켓을 다시 읽어 값이 들어갔는지 확인한다. 필드가 프로젝트 화면에 없어 실패하면 그 사실만 한 줄로 알리고 넘어간다.
- 텍스트만 받는 경우에는 본문 위에 `시작일: 2026-10-23 / 종료일: 2026-10-30` 한 줄로 같이 준다 (본문 세 섹션에는 넣지 않는다).

### 제목

핵심 한 줄, 60자 이내. 접두어(`[영역]` 같은 태그)는 붙이지 않는다. 프로젝트와 컴포넌트는 Jira 필드가 담당한다.

- "~이 안 됨", "~ 추가", "~ 개선"처럼 무엇이 문제이거나 무엇을 할지 바로 드러나게
- 피할 것: "문의", "확인 요청", "이슈 있음" 같은 내용 없는 제목

예:
- `쿠폰 적용 후 결제 금액이 0원으로 표시됨`
- `프로필 이미지 업로드 용량 제한 10MB로 상향`

### 본문

세 섹션 고정. 이름을 바꾸거나 추가하지 않는다. 해당 없는 섹션은 "해당 없음"이 아니라 아예 뺀다.

```
Background
* (왜 하는지 / 어떤 문제인지)

Deliverable
* (무엇을 만들거나 고치는지)

Output
* (끝났을 때 무엇이 나오는지, 확인 기준)
```

섹션 이름은 헤딩(`h3.`, `###`)이나 볼드 없이 일반 텍스트 한 줄로 쓴다.

#### 줄바꿈과 간격 (Jira에서 깨지지 않게)

헤딩이 없으면 섹션은 줄바꿈으로만 구분된다. 간격이 무너지면 세 섹션이 한 덩어리로 붙는다. 다음을 지킨다:

- 섹션 이름은 자기 줄에 단독으로, 앞에 빈 줄 하나를 둔다. 빈 줄이 없으면 Jira가 섹션 이름을 앞 불렛 목록에 붙여 렌더링한다.
- 섹션 이름 바로 다음 줄부터 불렛 시작. 사이에 빈 줄을 넣지 않는다 (넣으면 이름과 목록이 떨어져 보인다).
- 불렛은 `* ` (별표+공백)으로 줄 맨 앞에서 시작. 들여쓰기나 `-`를 섞지 않는다. Jira 위키 마크업과 마크다운 양쪽에서 똑같이 목록으로 잡힌다.
- 커넥터로 생성할 때는 줄바꿈을 실제 개행 문자로 넣는다. `\n`을 문자열로 넘기거나 한 줄로 이어 붙이지 않는다.
- 생성 후 가능하면 티켓을 한 번 읽어 세 섹션이 나뉘어 보이는지 확인한다. 붙어 있으면 섹션 앞 빈 줄을 추가해 수정한다.

본문은 "빈 줄 → 섹션 이름 → 불렛들" 블록 세 개가 이어진 모양이 된다. 첫 섹션 앞의 빈 줄은 생략한다.

#### 문체: 음슴체 불렛

각 항목은 한 줄, 음슴체로 끝낸다. "~함", "~임", "~됨", "~필요", "~예정".

- 좋음: `* 쿠폰 적용 시 할인액이 총액보다 커지면 음수가 0으로 클램핑됨`
- 나쁨: `* 쿠폰을 적용했을 때 할인액이 총액보다 커지는 경우에 음수 금액이 0으로 클램핑되는 것으로 보입니다.`

음슴체는 짧게 쓰려고 고르는 문체다. 문장이 길면 음슴체로 바꿔도 장황하다. 한 항목에 사실 하나만 담는다.

#### 짧게 쓰는 기준

- 섹션당 불렛 1~4개. 넘치면 가장 중요한 것만 남기고 나머지는 댓글로 돌린다.
- 인사말, 배경의 배경, "~로 보임/~인 것 같음" 같은 완충 표현은 쓰지 않는다. 사실은 단정형, 추측은 `원인 미확인`처럼 짧게 표시한다.
- 제목에 쓴 말을 본문에 반복하지 않는다.
- 긴 설명·대화 로그·코드를 받으면 요약해서 넣는다. 원문을 옮기지 않는다.
- 스크린샷·로그·링크는 본문에 풀지 말고 `첨부 참고` 한 줄로 가리킨다.

#### 정보가 부족할 때

Deliverable이나 Output을 채울 근거가 없으면 지어내지 말고 `* (확인 필요: ___)`로 자리를 남긴다. 초안을 보여주는 단계에서 빠진 것을 한 번에 묻는다.

### 댓글: AI 처리 상세

Claude가 조사하거나 처리한 일을 티켓으로 남길 때는 처리 과정의 상세를 본문이 아니라 댓글에 쓴다:

- 분석한 내용, 원인 추적 과정
- 변경한 파일·커밋·PR 목록
- 실행한 명령, 테스트 결과, 로그 요약
- 판단 근거와 남은 리스크

댓글도 불렛 음슴체로 쓰되 길이 제한은 본문보다 느슨하다. 첫 줄에 `AI 처리 상세`라고 적어 사람이 쓴 댓글과 구분한다. 텍스트만 줄 때는 본문 아래에 `---`로 구분해서 "댓글용" 블록으로 같이 준다.

처리한 게 없는 단순 티켓(사용자가 내용만 불러준 경우)이면 댓글을 만들지 않는다.

PR이 있어도 상세는 여기에 쓴다. PR 본문에는 요약만 두고, 긴 내용은 전부 이 댓글로 모은다.

### PR 링크

세션에서 코드 작업을 하고 GitHub PR을 만들었으면 티켓의 링크 영역에 PR을 "Link URL"(웹 링크, remote issue link)로 단다. 새 티켓뿐 아니라 기존 티켓을 다룰 때도 같다. 본문이나 댓글에 URL을 붙여 대신하지 않는다.

#### 링크 텍스트

```
#{pr-number}: {short-reponame}: {pr-title}
```

- `{short-reponame}`은 org를 뺀 레포 이름 (`jx2lee/claude-dotfiles` → `claude-dotfiles`)
- `{pr-title}`은 PR 제목 그대로. 줄이거나 바꾸지 않는다.
- 예: `#42: claude-dotfiles: work-item 스킬에 날짜 입력 추가`

#### 진행

1. PR 번호·제목·URL·레포를 확인한다. 세션 기록에 없으면 `gh pr view --json number,title,url,headRepository`로 가져온다.
2. 티켓의 기존 remote link 목록을 읽는다. 같은 PR URL이 이미 있으면 달지 않고 "이미 링크됨" 한 줄만 알린다. 링크 텍스트가 달라도 URL이 같으면 이미 링크된 것이다.
3. 없으면 remote link를 만든다. `object.url`에 PR URL, `object.title`에 위 링크 텍스트를 넣는다. 커넥터에 전용 도구가 없으면 `discover`로 remote link 생성 작업을 찾는다.
4. 만든 뒤 링크 목록을 다시 읽어 들어갔는지 확인한다.

PR이 여러 개면 PR마다 링크를 하나씩 단다. PR을 만들지 않았으면(커밋만 했거나 push 전이면) 링크를 달지 않는다.

### PR 본문

PR 본문도 Jira 본문처럼 사람이 몇 줄만 보고 파악하는 요약이다. 분석 과정, 파일별 변경 목록, 로그는 PR에 풀지 않고 Jira 댓글(`AI 처리 상세`)에 둔다.

```
Jira: {티켓 키 링크}

Summary
* (무엇을 바꿨는지)

Test
* (어떻게 확인했는지)
```

- 섹션 이름, 불렛, 음슴체 규칙은 Jira 본문과 같다. 섹션당 불렛 1~4개.
- 첫 줄 `Jira:`에는 티켓 URL을 링크로 건다. 티켓이 아직 없으면 이 줄을 빼고, 티켓을 만든 뒤 PR 본문에 추가한다.
- 배경 설명은 쓰지 않는다. 왜 하는지는 Jira 본문에 있다.
- 테스트를 안 했으면 `* 테스트 안 함 (이유)`로 적는다. 비워두지 않는다.
- 레포에 PR 템플릿이 있으면 템플릿을 따르고, 각 칸을 위 기준대로 짧게 채운다.

### 출력

- **생성**: 프로젝트와 이슈 타입을 확인한 뒤 생성. 생성 후 티켓 키와 링크만 한 줄로 알려주고, 날짜를 넣었거나 댓글·PR 링크를 남겼으면 그것도 한 줄로.
- **텍스트만**: 제목 한 줄 + 본문 코드블록 (+ 댓글용 블록). 앞뒤 설명 없이 그대로 복사할 수 있게.
